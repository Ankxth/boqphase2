| Area | Feature | Notes |
|---|---|---|
| **Auth** | Email/password + OAuth (Google/Microsoft) login, JWT or session-based auth, password reset flow, email verification | Standard FastAPI stack: `fastapi-users` or a hand-rolled JWT layer + `passlib` for hashing. Needed before any real user data touches this. |
| **Auth** | Role-based access (admin / engineer / viewer) | A viewer should see results but not edit substitution parameters or delete projects; an admin manages org-wide settings. |
| **Security** | HTTPS everywhere, CORS locked to real production origins (not `localhost:5173`) | The current CORS config is dev-only by design — flagged in `main.py`'s own comment. |
| **Security** | Rate limiting on `/boq-carbon/calculate` and `/form` | These accept file uploads and run real compute; unthrottled, they're a DoS/cost vector. |
| **Security** | File-upload validation beyond extension check (magic-byte sniffing, max file size, virus/malware scan) | Current check is just `.xlsx`/`.xls` suffix — trivially spoofable. |
| **Security** | Secrets management (LLM API keys, DB credentials) via a vault/env-secret manager, not plain `.env` in production | `config.py`'s `LLM_PROVIDER` env pattern is fine for dev, not for prod secrets. |
| **Security** | Audit log of who ran what calculation, when, with what inputs | Needed for any client who'll use this for real GRIHA/EDGE-adjacent submissions — traceability matters for certification-adjacent numbers. |
| **Accounts** | User profiles (name, org, role), org/team model (multiple engineers sharing one company's projects) | Almost every real customer here is a firm, not a lone user — multi-seat from day one saves a migration later. |
| **Project storage** | Persistent per-user/per-org project store (currently `project_store.py` is file-based JSON — fine for one user, not for concurrent multi-user access) | Move to Postgres (or similar) with proper project ownership, not a shared JSON file on disk. |
| **Project storage** | Versioning — re-running a project after editing the BOQ or tiered inputs should keep history, not overwrite | Useful for "how did our number change after we swapped to GGBS" tracking, which ties directly into the substitution feature. |
| **Project storage** | Uploaded BOQ files retained (with the org's consent/data-retention policy) so a project can be re-opened without re-uploading | Currently Phase 2's uploads are temp files deleted after calculation — fine for a stateless API, not for a "reopen my project" UX. |
| **Backend** | Async job queue for large BOQs (Celery/RQ + Redis, or FastAPI background tasks) | A 2,000-row BOQ calculates in ~1 second today; that's fine, but a real product should not block an HTTP request on file processing as usage scales. |
| **Backend** | Structured logging + error monitoring (Sentry or similar) | Right now failures print to stdout — fine for you pasting output back to me, not for production support. |
| **Backend** | API versioning (`/v1/boq-carbon/calculate`) | So future breaking changes to the schema don't silently break existing frontend clients. |
| **Backend** | Automated tests (the `scripts/test_*.py` files are manual — no CI, no assertions) | Turn `test_boq_carbon_pipeline.py` and `diagnose_coverage_gaps.py` into real pytest cases with the 5 reference BOQs as fixtures, so a classifier-ordering change (like the plaster/steel one found above) gets caught automatically instead of by manual re-running. |
| **Frontend** | Authenticated routes, a real project list/dashboard landing page (not "start at the tiered form every time") | Ties into project storage above — a returning user should land on "your projects," not step 01 of a fresh estimate. |
| **Frontend** | File-upload progress/cancel for large BOQs, and graceful handling of a backend that's mid-deploy | Currently a network failure just shows the raw error message. |
| **Frontend** | Accessibility pass (contrast, keyboard nav, screen-reader labels) | The blueprint palette's cyan-on-paper and safety-orange text should be checked against WCAG AA contrast ratios before this goes external. |
| **Compliance** | Data residency/privacy policy for uploaded BOQs (these contain real project costs and quantities — commercially sensitive) | Worth deciding early whether files are ever used to improve shared factors/models, since that has real client-trust implications. |
| **Compliance** | A documented factor-provenance page (which numbers are IFC-verified vs. placeholder, versioned) | You already have this ethos baked into the code (`factor_disclaimer`, `scope_note`) — surfacing it as a real, dated methodology page is what turns "trust us" into something an EDGE/GRIHA assessor can actually cite. |
